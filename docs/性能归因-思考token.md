# 性能归因：80% 的成本花在用户看不见的地方

## 现象

流式输出，但"首字时间"比"非流式总耗时"还长。这两个数自相矛盾——流式本该更快看到第一个字，结果反而更慢。

| | 非流式 | 流式 |
|---|---|---|
| 看到第一个字 | 24.57s | 29.84s |

第一反应是"流式没生效"或者"网络慢"。都是错的。

## 归因过程

用 `diag_stream.py` 做三组对照，把变量一个个排除：线路 → 服务端 → 模型行为。

| 测试 | 做法 | 结果 | 结论 |
|---|---|---|---|
| T1 | 极小问题 + 非流式 | 4.04s / 202 token | 线路正常，不是网络问题 |
| T2 | 极小问题 + 流式 | 3.91s 首字 / 1 个 chunk | 服务端确实在流式返回，不是假流式 |
| T3 | 原问题 + 流式 | 首字 23.87s，期间收到 30 个 chunk、4644 字符 `reasoning_content` | **首字前那 20 秒，模型在思考** |

关键证据是 T3：`delta.content` 一直为空，但 `delta.reasoning_content` 在疯狂输出。这是推理模型（`qwen3.6-plus`）特有的字段——思考阶段不产生正文，所以"首字时间"停在了思考结束的那一刻。

**流式没坏，是模型在思考，而思考过程不算正文。**

## 量化

同一个问题（"用三句话解释 RAG，给个电商售后例子"），只切换 `enable_thinking`：

| 指标 | 思考开（默认） | 思考关（`THINK=0`） | 倍数 |
|---|---|---|---|
| 正文首字 | 35.72s | **0.91s** | 快 39 倍 |
| 总耗时 | 38.45s | **2.46s** | 快 15.6 倍 |
| 输出 token | 2211 | **103** | 少 21 倍 |
| 单次成本 | ￥0.017738 | ￥0.000878 | 便宜 20 倍 |
| 思考内容 | 5883 字（不计入正文） | 无 | — |

## 结论

**思考 token 按输出 token 计费。** 一句两三百字的回答，账单按 2200 token 算。所以成本问题的根子不在"输出太长"，而在"用户看不见的思考"。

处理方式：**按场景分流**。

| 场景 | 是否开思考 | 理由 |
|---|---|---|
| 在线客服问答 | 关 | 用户盯着屏幕等首字，0.9s 和 35s 是两种产品 |
| 离线工单批量分析 | 开 | 没有人在等，质量优先 |

代码里就一行：`extra_body={"enable_thinking": False}`。

## 为什么记这一笔

面试里说"我做了缓存、做了优化"没有说服力——谁都能说。有说服力的是：**先归因，量出 80% 的成本花在一个用户看不见的环节上，再按场景分流。** 顺序是"定位 → 量化 → 分流"，不是"照着博客加缓存"。
