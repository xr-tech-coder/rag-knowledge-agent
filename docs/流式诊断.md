# 流式没生效？先分清是哪种"慢"

看到"首字 30 秒"时，不要直接改代码。慢有三种完全不同的原因，处理方式完全不同：

| 原因 | 表现 | 处理 |
|---|---|---|
| 线路 / 服务商排队 | 非流式也一样慢 | 换线路、换时段，别怪流式 |
| 服务端缓冲（假流式） | chunk 一次性涌出 | 换服务商，或改用 SSE |
| 推理模型在思考 | 首字前有 `reasoning_content` | 关思考，或把 TTFT 拆成"思考时长 + 首字时长" |

## 三组诊断

```bash
diag.bat
# 或
.venv\Scripts\python.exe diag_stream.py
```

| 测试 | 做什么 | 排除什么 |
|---|---|---|
| T1 | 极小问题 + 非流式 | 线路/排队（与流式无关的慢） |
| T2 | 极小问题 + 流式 | 服务端是否"攒完才发" |
| T3 | 原问题 + 流式 | 逐 chunk 时间线，看首字前在干什么 |

## 判据

- **T2 chunk 数 ≤ 3 且首字 ≈ 总时长** → 服务端缓冲，假流式（中转/代理常见）
- **收到 `reasoning_content`** → 推理模型，思考阶段不产生正文，TTFT 要另算
- **T1 也要十几秒** → 基线就慢，先换线路/时段，别在流式代码里找原因

## 计时怎么拆

`main.py` 把首字拆成两段分别计时，避免把思考时间算进"生成速度"：

```
思考耗时（发出请求 → 首个 reasoning_content）
正文首字（发出请求 → 首个 content）
总耗时
```

结论行是按实测数据**判断**出来的，不是写死的字符串。数据变了，结论跟着变——否则下次别人跑出不同结果，这份报告就成了假证据。
